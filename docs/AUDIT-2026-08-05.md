## Critical (all 4 verified confirmed)

### C1 — Resend quota errors never trip the rate-limit breaker
`src/lib/notifications/rate-limit.ts:24` — `isResendRateLimitError` matches only `error?.name === "rate_limit_exceeded"`. Resend's quota exhaustion errors are named `daily_quota_exceeded` / `monthly_quota_exceeded` (documented in CLAUDE.md Infrastructure Limits). On the day the 100/day free-tier cap runs out — by definition the highest-alert-volume day — the breaker never trips, every pending alert is attempted and fails, and (via C2) each is marked dispatched and never retried after the quota resets. Fix: add both quota error names to the matcher (they should stop the run exactly like a rate limit; the alerts then retry next tick / next day under the durable `dispatched_at IS NULL` query).

### C2 — Attempted-but-failed sends are marked dispatched (permanent loss)
`src/lib/notifications/dispatch.ts` (~lines 323-356): `completeWork(alertId)` is called unconditionally after `sendAlertToUsers` returns — even if `sent < userIds.length`, even if every send failed. Same in the digest path: `ok === false` still runs `completeWork` for every alert in the digest. And `sendAlertToUsers` (`src/lib/notifications/send.ts:100-120`) never checks `isRateLimited()` between its internal batches of 10, so the alert in flight when a rate limit hits burns through its remaining users and is then marked dispatched. This contradicts the layer's own documented guarantee ("anything left mid-flight stays undispatched and is re-fetched whole on the next tick") — that guarantee only covers alerts the run never *started*, not ones that started and failed. Any transient send failure is a permanent per-user miss. Fix: only `completeWork` when the sends actually succeeded (or make per-user failure re-eligible next tick — the `alreadySentPairs` dedup already makes retrying a partially-sent alert safe), and check `isRateLimited()` inside `sendAlertToUsers`' batch loop.

### C3 — pricedUpcoming's alert-history guard is unpaginated (false out_now emails return past 1,000 rows)
`src/lib/nintendo/ingest.ts` (~line 1193): the guard that prevents the documented 62-alert false "out now" incident fetches `alerts.select("game_id").in("game_id", ids)` with no limit handling. PostgREST caps at 1,000 rows; the incident-class games carry 20-40 alert rows each, so a recovery wave of ~30+ candidates truncates the result and history-having games read as "genuinely new" → false out_now emails via franchise fanout. Verified that the out_now breaker does NOT catch this case: its live re-verification checks `sales_status === "onsale"`, which a long-released game recovering from $0 corruption genuinely satisfies. The one guard that exists for this exact scenario silently fails at exactly the scale the scenario produces. Fix: paginate the history query (or check per-game existence).

### C4 — Alert dismissal silently lost when navigating during the undo window
`src/app/alerts/page.tsx` (~lines 80-84): dismissal is optimistic in the UI with the DB write delayed 5s for the undo toast. The unmount cleanup runs `clearTimeout(pendingTimer.current)` without calling `commitPending` — so dismiss → tap another alert (or Clear all → switch tabs) cancels the write entirely and the alerts reappear on next load. A silent no-op of a user action. Fix: commit pending dismissals in the cleanup (fire-and-forget) instead of just clearing the timer.

## Moderate — verified this session

- **Founder slate dates were one nightly sync from reverting** — the 2026-08-05 slate script tagged rows `release_date_source='nintendo'`, which the catalog sync's trusted-date restore pass (`ingest.ts:268`) didn't recognize. **Fixed and deployed this session (`cbe8d48`)** before the 21:00 UTC sync. Residue, not yet fixed: the script's 8 created rows (FireRed/LeafGreen etc.) have NULL `franchise`, so franchise followers won't get alerts for them.
- **Push endpoint hijack (audit #10) was never actually fixed** — `src/app/api/push/subscribe/route.ts:26-31` still upserts `onConflict: "endpoint"`, reassigning `user_id` for an existing endpoint. Zero production subscribers today, but do not copy this pattern into the mobile device-token path.
- **Sale-flap dedup only covers `sale_started`** — `isDuplicateSaleSignature` is called only under `isNewSale` (`ingest.ts:808`); the `price_drop` branch can re-fire an identical flap signature at >24h gaps. The Monster Hunter flap incident replayed today would email duplicates as price drops.
- **Health-check doesn't monitor Launch Burst Poll** — `MONITORED_CRON_TITLES` (`health-check/route.ts:15`) lists 9 jobs; the launch-minute differentiator cron is absent, unprotected against the auto-disable failure mode that has already killed 3 jobs unnoticed for months.
- **Stuck-placeholder invariant can never fire for its real target** — it filters `.lt("updated_at", 7d ago)` (`health-check/route.ts:247`), but price polling bumps `updated_at` on every actively-priced game every ~5h. The check only catches unpriced rows; a priced-but-stuck game is invisible to it.
- **`getUserProfile` still swallows its error** (`queries.ts:523-533`) — on a transient failure it returns `onboardingCompleted: false` and `/home` redirects an onboarded user back into onboarding. Flagged 2026-08-02 as follow-up hardening; never done.
- **Franchise pages are the one discovery surface with no junk filter** — `getGamesByFranchise` (`queries.ts:336`) has no `is_suppressed`/`product_type` filter; Monster Hunter / Dragon Quest franchise pages (the founder's own follows) still render suppressed DLC kits and bundles.
- **`getUnreadAlertCount` read-statuses fetch is unbounded** (`queries.ts:651-655`) — the alerts side caps at 50 but the `user_alert_status` read-rows side has no limit; past 1,000 read rows the nav badge overcounts. Fourth instance of the unbounded-select class, first client-side.
