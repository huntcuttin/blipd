overnight incident chain. This file is the execution reference for the follow-up work loop.
Everything here was verified against live production data or current code with file:line

## 0. Headline findings (what the audit found that we didn't know)

1. **The false out_now wave was NOT over when the overnight session said it was.** 489
   out_now alerts fired on 2026-08-03 (vs zero/day the prior 6 days), continuing until
   13:10 UTC — hours after the "fix holds" verification. 8 more junk DLC emails reached
   the founder's inbox at 10:20 UTC. The session log's claim that "Hunting Simulator" and
   "Bayonetta Origins" were genuine launches was **wrong** — Bayonetta Origins released
   March 2023; both were false positives. Root cause of the guard failure: the
   prior-alert-history guard passes any game with no alert history, and **iconic Nintendo
   games whose prices never changed have no alert history** — the guard is structurally
   blind to exactly the most famous titles. The trap is now exhausted (0 rows currently
   match the fallback condition), but 384 unsuppressed rows sit at released+placeholder-date,
   each having burned its one-time false alert.
2. **product_type is NULL on 100% of rows.** The shipped UI filter
   (`.or("product_type.is.null,...")`) currently filters *nothing*. Worse, the daily
   catalog sync can never backfill junk rows: `isStandaloneGame()` drops ADD_ON_CONTENT
   hits *before* `algoliaHitToGameRow` runs, so the only rows that would get labeled are
   exactly the rows that don't need labeling. **A one-time explicit backfill is mandatory,
   not optional.**
3. **Five live email holes remain open right now** (see §2). The most imminent: suppressed
   junk rows are still fully alive in the *price-alert* path (the poll query never filters
   `is_suppressed`), and Capcom's Monster Hunter promo — which includes DLC SKUs — runs
   through Aug 18. The founder follows the Monster Hunter and Dragon Quest franchises.
4. **Cover art is broken on virtually every game card** across /deals, /sales, /feed, and
   game detail (broken-image icons, "No image" fallbacks) — the single biggest visual
   credibility problem for a launch-post audience. Likely Nintendo CDN hotlink blocking or
   dead URLs; diagnose before fixing.
5. **The game detail page publicly displays fabricated data**: "Released April 1, 2026"
   for Monster Hunter Rise + Sunbreak (a 2022 bundle — the date is the alert-history-anchored
   estimate from the overnight cleanup), plus a wall of 10+ visually identical duplicate
   "SALE STARTED" alert cards that directly contradicts /vs/nt-deals' anti-spam pitch on
   the same site.
6. **`email_suppressions` is written by the bounce webhook but read by nothing.** Bounce
   suppression does not suppress. The launch-readiness item marked "fully done" is half-done,
   and Resend pauses ALL sending account-wide at 4% bounce rate.
7. **Any alert older than 15 minutes at dispatch time is silently never emailed.** No
   durable queue, no retry, no backlog scan. A missed dispatch run (cron auto-disable,
   deploy race, Resend 429 storm) permanently eats alerts. This is the single biggest
   structural gap against "the alert fires."

## 1. The amended architecture (post-critique, final)

The draft architecture survived review with these amendments. This is the target state.

### A. One persisted classification signal: `games.product_type`
- Values: `TITLE` | `ADD_ON_CONTENT` | `BUNDLE` | `UNKNOWN`. Source: Nintendo's own
  Algolia `eshopDetails.productType`. Column exists (migration 20260803_007); ingest
  writes it (transform.ts).
- **One-time backfill of all ~2,934 rows** via per-nsuid Algolia lookup. Method constraints
  proven this session: nsuid-as-query-text works, facet filtering does NOT; verify the
  returned hit's nsuid matches exactly before trusting it; when `eshopDetails` comes back
  literal null (3 observed), fall back to `topLevelFilters` containing 'DLC' / `hasDlc`.
  Rows unresolvable after retries (nsuid-null placeholders, rotated-out listings) get
  **`UNKNOWN`** — a terminal state, never a perpetual alarm. Ship as a saved `fixes/` script.
- Post-backfill, NULL is only legal on rows `created_at` after the backfill date; the
  health-check invariant keys on that.
- This matches the industry-standard model: DekuDeals (`filter[type]=dlc`), ITAD
  (game/dlc/package), PlatPrices (`hidedlc=1` — games-only is their *default*). No mature
  tracker uses title heuristics.

### B. Asymmetric whitelist (the core Bible-driven rule)
Fail-open toward directly-followed users; fail-closed toward franchise fanout and discovery.
- **Franchise-follow fanout: strict `product_type='TITLE'` only.** NULL/UNKNOWN excluded.
  Every junk email in every incident traveled this path. Enforce it defensively in
  `dispatchRecentAlerts` (a game-level re-check on the alerts→games join), because dispatch
  is the one funnel every creation path passes through.
- **Direct game follows are sacred, everywhere**: alert creation, burst-poll targeting,
  and dispatch never filter a directly-followed game by product_type OR is_suppressed.
  (Live bug: the founder's followed "Dave the Diver: In the Jungle" is `is_suppressed=true`
  and can currently never alert — a Product Bible violation.)
- **Discovery surfaces (Out Now, Coming Soon, /deals, /sales)**: keep the null-lenient
  blacklist (`NOT IN (ADD_ON_CONTENT, BUNDLE)` with NULL included) — after backfill NULL≈0
  so the semantics converge; the null-lenient OR was a deliberate, commented decision.
- **launch-burst-poll gets NO product_type filter** — its candidate set is already derived
  from user_game_follows, i.e. it is a personal-watchlist surface ("quality filters apply
  to discovery, never to personal watchlists").
- Permanently filter-exempt surfaces, stated explicitly: Home dashboard, /alerts feed,
  profile watchlist, search results, game detail.

### C. Date provenance: three legal writers, zero guessing
- Legal `release_date` writers: **IGDB sync**, **Algolia's `releaseDate` field**, and
  **price-confirmed** (the date the pipeline actually observed `sales_status` flip to
  onsale — ground truth, not a guess; it is also the only un-sticker for games IGDB can't
  match, and the D4 invariant depends on it). Each tagged in `release_date_source`.
- Banned forever: dates inferred from title text, publisher patterns, "probably today"
  fallbacks, or alert-history anchoring (the "Released April 1, 2026" class).
- Display rule: never render an estimated/unknown date as fact. Placeholder renders "TBA".
- `release_date_precision` column: **killed** (POC critic) — encode sentinel-date exclusions
  directly in invariant SQL instead (Dec-31 = year-only, month-end = month-only).

### D. Catalog-integrity invariants (in the existing 30-min health-check)
All invariants **email the admin and never block, delay, or filter any alert or dispatch
path** (state this in the code comment). Each threshold constant gets a comment naming the
real-world event that sets its floor.
1. Mass-date detector: >50 unsuppressed rows sharing one non-sentinel release_date written
   within 24h (excludes 2099-12-31, any Dec-31, any month-end; excludes daily-sync bulk writes).
2. Junk leak: any ADD_ON_CONTENT/BUNDLE row currently matching Out Now/Coming Soon
   eligibility (regression trap for the exact incident class).
3. product_type NULL on rows created after the backfill date > small threshold.
4. Unsuppressed placeholder-dated row with a real price persisting >7 days.
5. out_now alert volume, two-tier: >15/60min = informational line; >50/60min = alarm.
   (Launches cluster at 9AM PT / 9PM PT / midnight ET, so a real Direct-day wave can
   legitimately exceed 15 in one window.)

### E. Launch-alert flood protection: three stateless layers, no human gate
Replaces the rejected "quarantine" design. No new state, no release valve, no human in the
delivery path — a quarantined real launch alert under monthly-check-in ops is not late, it
is dead.
1. **Per-user launch digest (already shipped in batching.ts — keep, verify, document):**
   ≥5 launch alerts per user per run → exactly one digest email. This alone bounds a fully
   fooled flood to one email per user.
2. **Event-creation breaker** (in update-prices + burst-poll, before alert rows insert):
   if a single run produces >20 out_now candidates, re-verify each inline in the same run —
   (a) Nintendo live price API `sales_status=='onsale'`, (b) product_type rule per §B,
   (c) `is_suppressed=false` (unless directly followed), (d) zero prior alerts of any type,
   (e) non-placeholder date or `release_date_source='price-confirmed'`. Verified candidates
   insert and dispatch in the SAME run (one batched API call of added latency); failures are
   never inserted and produce one admin email. Rationale: every historical junk alert failed
   at least one of these cheap checks.
3. **Absolute ceiling:** >100 verified candidates in one run (no real day reaches this) →
   hold that run's inserts, alarm, auto-release candidates that pass verification on two
   consecutive polls (~10–20 min worst case, never a month).
Also: capping on the event side protects the Resend 100/day quota — a junk flood reaching
dispatch starves every REAL email for the rest of the day, which is itself a lateness failure.
Direct-follow sends are exempt from any cap at every layer.

### F. Change discipline (goes in CLAUDE.md, enforced by a script)
- Governed shared signals: `is_suppressed`, `product_type`, `release_date` semantics /
  placeholder conventions, `release_date_source`.
- Any edit touching one: grep all consumers first; then run
  **`fixes/verify_catalog_surfaces.sh`** (to be created: runs the literal production
  queries for Out Now / Coming Soon / Deals and prints the top 20 titles each) and eyeball
  the output before commit; paste the output summary into the commit message.
- Manual cron re-triggering during verification: stop after 2 confirming runs (the
  deploy-propagation race + today's 489-alert wave were both amplified by repeated manual
  triggers).
- When counting anything ("did X false thing happen"), run the unbounded defining-condition
  query first — three successive undercounts happened this session from narrow windows.
- Never claim "verified live" without confirming the deployed commit SHA matches HEAD.

## 3. PHASE 1 — Structural alert correctness

10. **email_suppressions enforcement**: shared `isEmailSuppressed()` (batch-fetch the set
    once per dispatch run) checked before EVERY `resend.emails.send` — email.ts,
    send-batch.ts (both send sites), weekly-digest.
11. **Durable dispatch**: replace the `now()−15min` window with a persisted watermark or an
    undelivered-work query (alerts from last N hours lacking a status='sent'
    notification_log row — the alreadySentPairs machinery already makes this idempotent).
    Add `.range()` pagination to the alerts fetch (silently truncates at 1,000 today).
    Treat a Resend 429 as stop-the-run, not log-failed-and-continue.
12. **Event-creation breaker + ceiling** (§E layers 2–3) in update-prices and burst-poll.
    Verify layer 1 (launch digest in batching.ts) with a test and document it as the spam
    bound.
13. **computeReleaseStatus timezone fix** (transform.ts): it uses UTC "today" while
    runReleaseStatusUpdate uses Pacific — from ~4-5pm PT, sync-release-dates and catalog
    sync stamp release-day games 'out_today' a day early, which makes releasingToday SKIP
    their launch-day alert (matches status='upcoming' only). **This is a launch-day alert
    MISS bug — the Bible's worst failure.** Export one Pacific date helper; use it everywhere.
14. **Ingest gate parity**: `isStandaloneGame` blocks ADD_ON_CONTENT but not BUNDLE — add
    it ("...Legend Edition Year 2" matches no title regex and refills the trap).
    searchGames: filter Algolia hits on `eshopDetails.productType` (null-lenient; keep
    isAddon as secondary net) and add is_suppressed to the DB announced branch — search is
    how users can still follow junk.
15. **Sale surfaces**: add the product_type OR-filter to getGamesOnSale and /deals SSR
    (junk carries the deepest discounts and /deals emits schema.org into Google).
16. **sync-release-dates no-match marker**: mirror the sibling syncs — on attempted-no-match
    write `release_date_checked_at` (or source='igdb-no-match') and deprioritize in the
    queue for N days. The alphabetical-jam class (two incidents) is otherwise structurally
    intact with BATCH_SIZE=10. The 384 released-at-placeholder rows are this queue's
    natural workload once unjammed.
17. **Suppression semantics split**: `is_suppressed` means duplicate-listing AND junk AND
    delisted, and catalog sync's dedup pass unconditionally un-suppresses "base" rows
    (ingest.ts ~:477) — it can silently resurrect manually-suppressed junk daily. Cheapest
    fix: add `suppression_reason` text column ('duplicate'|'junk'|'delisted'); dedup pass
    only clears its own reason. Alternative if avoiding schema change: skip un-suppress when
    product_type is ADD_ON_CONTENT/BUNDLE.
18. **Sentinel/predicate consistency**: export PLACEHOLDER_DATES from format.ts as the
    single source, use everywhere ('2020-01-01' is honored by only half the consumers);
    standardize `.eq("is_suppressed", false)`.
19. **Smaller alert-path items**: IGDB release_dates query should request the `category`
    (precision) field and refuse/tag non-exact dates + not take `limit 1` arbitrarily
    across two platforms; named-sale blast should write notification_log rows and key
    dedup on sale identity (name+end date), not detection day; weekly-digest should skip
    users with zero on-sale games and check suppressions (real opt-out toggle = Phase 4);
    detect-trailers should route through insertAndDispatch (low priority — YouTube RSS is
    dying anyway); fix the spurious "failed web_push" notification_log rows for push-less
    users (distinguish no-subscriptions from all-failed); retro_game_added has no email
    template (silently no-ops — add template or document email-exempt).

## 6. PHASE 4 — Features (survivors of the Wednesday-night test, 4 of 12)

In order. Features 2 requires founder sign-off on email copy BEFORE sends are enabled
(locked Bible rule: any notification/email template change prompts the founder).
1. **Last-checked freshness stamp** (S) — same as item 27; it's simultaneously the #1
   feature and a compliance gap.
2. **Date-locked alert (`release_date_set`)** (M) — new alert type when a FOLLOWED game's
   placeholder date resolves to a real date. Hook: sync-release-dates' placeholder→real
   write + catalog sync's releaseDate fallback. Fires ONLY on placeholder→real transitions
   (never real→real — date fields flap), only for followed games, through the existing
   notify_releases fanout. Needs: getPrefColumn entry, email template (draft, then STOP for
   founder sign-off), dedup guard. This converts the thin-dated-catalog weakness into the
   anticipation beat of the hero moment.
3. **Precision-aware Coming Soon sectioning** (S) — This week / This month / Later / TBA
   buckets via existing isMonthOnlyDate(); honest "TBA 2026" labels.
4. **"On the Horizon"** (S) — the TBA bucket surfaces the ~312 genuine unsuppressed
   undated upcoming titles that are completely invisible today, each with a follow CTA
   ("get told the minute this gets a date — and the minute it launches"). This is the
   top-of-funnel for launch-burst-poll, which only watches followed games. Ships with #3.

Killed (do not build): per-game freshness timestamps (manufactures doubt), launch-eve
reminder emails (noise between Wednesdays by definition), predicted go-live on detail page
(duplicate of /release-time). Deferred: real→real date-change alerts (highest false-alert
risk until date fields prove stable), franchise "new title announced" (wait 2-3 clean
check-ins on the ingest guard), countdown chips, tracked-since label, out-now email
freshness line (bundle with the voice decision).
